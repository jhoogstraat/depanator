# Homelander scraping and approval-gated apartment agent analysis

## Source scope and confidence

This report uses Homelander’s first-party GitHub repository: [B1Z0N/homelander](https://github.com/B1Z0N/homelander). The inspected source is pinned to commit `b0e7283b540d853311854d5111bffc0254d5ea85`. All code links below use this immutable commit permalink. The repository-root `AGENTS.md` is the only applicable agent instruction file. No live site was visited or verified; API observations below are source code and test assertions, not independent live verification.

The repository-root [AGENTS.md](https://github.com/B1Z0N/homelander/blob/b0e7283b540d853311854d5111bffc0254d5ea85/AGENTS.md#L23-L66) describes architecture and flow; it is repository documentation, not a substitute for the implementation. It identifies Electron, a forked `engine/daemon.js`, Puppeteer/CDP via `engine/is24-contactor.js`, `engine/url-translator.js`, and `engine/db.js`, and states that poll discovers listings while a separate apply loop processes them. Its stack and data notes describe local SQLite and an IS24 Chrome profile ([AGENTS.md stack/architecture](https://github.com/B1Z0N/homelander/blob/b0e7283b540d853311854d5111bffc0254d5ea85/AGENTS.md#L9-L75), [AGENTS.md data layout](https://github.com/B1Z0N/homelander/blob/b0e7283b540d853311854d5111bffc0254d5ea85/AGENTS.md#L126-L153)).

## Verified source behavior

### Search URL, polling, and pagination

`engine/daemon.js` imports `fetchListings` from `url-translator.js` and runs independent poll/apply loops ([daemon imports and loop overview](https://github.com/B1Z0N/homelander/blob/b0e7283b540d853311854d5111bffc0254d5ea85/engine/daemon.js#L1-L18)). Each poll traverses enabled filters and asks for pages 1 through 5, with a nominal page size of 20. It stops on an error, a short page, or when a page adds zero new rows. On a filter’s first poll, it inserts at most 10 listings to avoid queueing the entire existing result set. It optionally excludes titles containing “tauschwohnung” and filters IDs already manually applied ([daemon poll loop](https://github.com/B1Z0N/homelander/blob/b0e7283b540d853311854d5111bffc0254d5ea85/engine/daemon.js#L676-L749)). The “poll now” path repeats the same 5-page/20-item/first-poll-10 behavior ([daemon manual poll path](https://github.com/B1Z0N/homelander/blob/b0e7283b540d853311854d5111bffc0254d5ea85/engine/daemon.js#L790-L836)).

The root AGENTS document says a user-provided web search URL is validated, translated to mobile API parameters, and persisted, and names `api.mobile.immobilienscout24.de/search/list` as the endpoint ([AGENTS.md key flow](https://github.com/B1Z0N/homelander/blob/b0e7283b540d853311854d5111bffc0254d5ea85/AGENTS.md#L60-L66)). The source implementation is `parseSearchUrl()` → `validateSearchUrl()` → `buildMobileApiUrl()` → `fetchListings()` in `engine/url-translator.js`. It accepts only an IS24 host with a `/Suche/` path; the final path segment identifies property type, preceding segments are region geocodes, and radius searches require a valid `geocoordinates=lat;lon;km` query. It maps apartment/house rent/buy and plot-buy slugs, selected SEO slugs, warm-rent paths, price, room count, living area, price type, heating, equipment, apartment type, and known direct API filters ([translator lines 8–92](https://github.com/B1Z0N/homelander/blob/b0e7283b540d853311854d5111bffc0254d5ea85/engine/url-translator.js#L8-L92), [lines 221–243](https://github.com/B1Z0N/homelander/blob/b0e7283b540d853311854d5111bffc0254d5ea85/engine/url-translator.js#L221-L243), [lines 523–717](https://github.com/B1Z0N/homelander/blob/b0e7283b540d853311854d5111bffc0254d5ea85/engine/url-translator.js#L523-L717)). It builds requests to the IS24 mobile `/search/list` API, supplies `sorting=-firstactivation`, `pagenumber`, and `pagesize=20`; `fetchListings` POSTs JSON with fixed User-Agent/Accept headers and detects HTML responses as perimeter captcha ([lines 724–779](https://github.com/B1Z0N/homelander/blob/b0e7283b540d853311854d5111bffc0254d5ea85/engine/url-translator.js#L724-L779), [lines 907–955](https://github.com/B1Z0N/homelander/blob/b0e7283b540d853311854d5111bffc0254d5ea85/engine/url-translator.js#L907-L955)). Safe tracking, sorting, and pagination query params are discarded. `fetchListings()` uses `validateSearchUrl()`, which rejects dangerous unknown query parameters; mobile-rejected filters are surfaced as safe-ignored warnings but do not make validation fail, so the request proceeds without those criteria. This silently broadens some searches unless the UI user notices the warning. Legacy `translateUrl()` does not run that strict validation, and its tests show unknown query keys stripped; use the validated fetch/import path for searches ([lines 209–243](https://github.com/B1Z0N/homelander/blob/b0e7283b540d853311854d5111bffc0254d5ea85/engine/url-translator.js#L209-L243), [lines 841–870](https://github.com/B1Z0N/homelander/blob/b0e7283b540d853311854d5111bffc0254d5ea85/engine/url-translator.js#L841-L870)). Tests cover common cities, property types, parameter mappings, ignored/rejected filters, and malformed URLs ([URL translator mapping tests](https://github.com/B1Z0N/homelander/blob/b0e7283b540d853311854d5111bffc0254d5ea85/test/url-translator.test.js#L178-L355), [URL translator unsupported/ignored filter tests](https://github.com/B1Z0N/homelander/blob/b0e7283b540d853311854d5111bffc0254d5ea85/test/url-translator.test.js#L590-L711)).

### Listing extraction and persistence

The translator extracts `expose_id` from `id` or `exposeId`; title; price from `price`, `totalRent`, or `purchasePrice`; area from `livingSpace` or `area`; room count; address line; and full/preview image URL from `resultListItems` ([URL translator extraction](https://github.com/B1Z0N/homelander/blob/b0e7283b540d853311854d5111bffc0254d5ea85/engine/url-translator.js#L931-L952); fixture coverage [extraction fixture tests](https://github.com/B1Z0N/homelander/blob/b0e7283b540d853311854d5111bffc0254d5ea85/test/url-translator.test.js#L1104-L1164)). **Material gap for LLM matching:** it does not extract listing descriptions, landlord details, or a full amenity/detail set into the normalized object. The contactor later navigates to an expose page for applying, but that is not a stored analysis snapshot. An LLM that must assess detailed listing prose/features therefore needs a separate page/API enrichment step and an immutable detail snapshot. Listing insertions go through `db.insertListings`; persistent states used by the daemon include `seen` and `processing`, while `markSent` records outcome/detail/time and appends a results row ([daemon claim/send path](https://github.com/B1Z0N/homelander/blob/b0e7283b540d853311854d5111bffc0254d5ea85/engine/daemon.js#L631-L653), [database outcome transaction](https://github.com/B1Z0N/homelander/blob/b0e7283b540d853311854d5111bffc0254d5ea85/engine/db.js#L309-L322)).

Before sending, the apply loop atomically changes a row from `seen` to `processing`; a failed claim skips the item. It then checks manual-application state and enabled-filter state before calling the contactor ([daemon claim/send path](https://github.com/B1Z0N/homelander/blob/b0e7283b540d853311854d5111bffc0254d5ea85/engine/daemon.js#L631-L653)). Successful submissions become `SENT`; ordinary failures become `FAIL`, `PREMIUM`, or `DEACTIVATED`. CDP-looking exceptions are put back to `seen`, while other exceptions are marked failed ([daemon apply failure handling](https://github.com/B1Z0N/homelander/blob/b0e7283b540d853311854d5111bffc0254d5ea85/engine/daemon.js#L288-L419)). Individual retry resets the selected expose row to `seen` regardless of its previous status (the database method only guards an already-`seen` row); retry-all includes `FAIL`, `SUBMIT_FAILED`, `SESSION_EXPIRED`, and `CAPTCHA`, subject to textual exclusions ([database retry behavior](https://github.com/B1Z0N/homelander/blob/b0e7283b540d853311854d5111bffc0254d5ea85/engine/db.js#L327-L348)).

The contactor also scrapes prior IS24 conversation expose IDs before applying, to protect against duplicates from applications sent outside the app. It pages the conversations API, extracts numeric `referenceId`s, and the contactor marks an unsuccessful response fail-closed ([Messenger duplicate preflight](https://github.com/B1Z0N/homelander/blob/b0e7283b540d853311854d5111bffc0254d5ea85/engine/is24-contactor.js#L599-L721); daemon preflight [lines 203–264](https://github.com/B1Z0N/homelander/blob/b0e7283b540d853311854d5111bffc0254d5ea85/engine/daemon.js#L226-L287)). However, the daemon only pauses on recognized expired-session or perimeter-captcha errors; other unsuccessful preflight responses are logged as warnings and then marked sync-complete, so sending can proceed without dedupe protection. This is site-specific behavior and should not be assumed for another listing site ([daemon preflight handling](https://github.com/B1Z0N/homelander/blob/b0e7283b540d853311854d5111bffc0254d5ea85/engine/daemon.js#L245-L278)).

### Details, account session, and message submission

`IS24Contactor.apply()` opens the listing expose page, checks login state, detects deactivated listings, opens the contact form, and checks whether the form is available. Login detection uses IS24’s JS flag and visible page text; an expired session is returned as a failure before filling ([contactor page/session checks](https://github.com/B1Z0N/homelander/blob/b0e7283b540d853311854d5111bffc0254d5ea85/engine/is24-contactor.js#L353-L407); [contactor login check](https://github.com/B1Z0N/homelander/blob/b0e7283b540d853311854d5111bffc0254d5ea85/engine/is24-contactor.js#L724-L748)). It fills the form with configured persona values and the supplied message ([contactor form fill](https://github.com/B1Z0N/homelander/blob/b0e7283b540d853311854d5111bffc0254d5ea85/engine/is24-contactor.js#L883-L930)). The message textarea is checked against the exact supplied string and repaired if the site’s React form reverts it ([exact message textarea check](https://github.com/B1Z0N/homelander/blob/b0e7283b540d853311854d5111bffc0254d5ea85/engine/is24-contactor.js#L1197-L1230)).

The daemon currently creates a message from a configured template by replacing `{{title}}`, `{{address}}`, and `{{name}}`, then calls `contactor.apply()` without an intervening human approval ([message personalization helper](https://github.com/B1Z0N/homelander/blob/b0e7283b540d853311854d5111bffc0254d5ea85/engine/daemon.js#L146-L151); [automatic apply call](https://github.com/B1Z0N/homelander/blob/b0e7283b540d853311854d5111bffc0254d5ea85/engine/daemon.js#L291-L321)). The contactor determines success from confirmation signals. Its verifier reports `SUBMIT_UNCONFIRMED` when the form closes without confirmation or no confirmation arrives within five seconds ([submission confirmation logic](https://github.com/B1Z0N/homelander/blob/b0e7283b540d853311854d5111bffc0254d5ea85/engine/is24-contactor.js#L1349-L1525)). More critically, `apply()` classifies `SUBMIT_UNCONFIRMED` as a validation error and can refill and click submit up to two more times ([contactor submission retry loop](https://github.com/B1Z0N/homelander/blob/b0e7283b540d853311854d5111bffc0254d5ea85/engine/is24-contactor.js#L465-L505)). If it finally returns failure, daemon records `FAIL`; retry-listing and retry-all can reset failed rows to `seen`, enabling another attempt ([daemon failure persistence](https://github.com/B1Z0N/homelander/blob/b0e7283b540d853311854d5111bffc0254d5ea85/engine/daemon.js#L340-L370), [database retry handlers](https://github.com/B1Z0N/homelander/blob/b0e7283b540d853311854d5111bffc0254d5ea85/engine/db.js#L327-L348)). This is a direct duplicate-send risk.

The authenticated IS24 session uses the user’s local Chromium profile and manual login; the repo instructions say to avoid automated login and check page text, not cookies alone ([AGENTS.md browser profile/login flow](https://github.com/B1Z0N/homelander/blob/b0e7283b540d853311854d5111bffc0254d5ea85/AGENTS.md#L68-L75), [AGENTS.md browser invariants](https://github.com/B1Z0N/homelander/blob/b0e7283b540d853311854d5111bffc0254d5ea85/AGENTS.md#L190-L194), [AGENTS.md session detection pitfalls](https://github.com/B1Z0N/homelander/blob/b0e7283b540d853311854d5111bffc0254d5ea85/AGENTS.md#L206-L211)). This is reusable only when the target site is IS24 and the user consents to reusing that local profile. The README warns that the project is educational and says use against IS24 is prohibited by its terms; that is the project’s own disclaimer, not an independent legal determination ([README disclaimer](https://github.com/B1Z0N/homelander/blob/b0e7283b540d853311854d5111bffc0254d5ea85/README.md#L107-L111)).

## Determinism, retry, and duplicate-send risks

“Deterministic scraping” can mean fixed parser and query logic, but cannot promise the same live result set across time: inventory, ranking, API response, and website behavior change. The implementation uses fixed page count, page size, sort, and normalized insertion path. Poll stops when a page inserts zero rows; because API sorting is newest-first this normally means all further pages are older, but inventory/order changes or gaps make this a heuristic rather than completeness proof. First poll caps queueing at 10 results; it does not establish a complete baseline. A duplicate key is a truncated SHA-256 of `expose_id|price`, so the same expose whose price changes can be inserted again as another row ([poll caps and stop conditions](https://github.com/B1Z0N/homelander/blob/b0e7283b540d853311854d5111bffc0254d5ea85/engine/daemon.js#L708-L749); [listing identity and insert logic](https://github.com/B1Z0N/homelander/blob/b0e7283b540d853311854d5111bffc0254d5ea85/engine/db.js#L200-L239)). Query mapping is code-deterministic but not lossless: mobile-rejected filters (including examples such as furnished, rental start date, WBS and has-pictures) are dropped with warnings; some heating/equipment values are silently removed because mobile API rejects or ignores them ([mobile unsupported filter declarations](https://github.com/B1Z0N/homelander/blob/b0e7283b540d853311854d5111bffc0254d5ea85/engine/url-translator.js#L341-L389), [mobile filter emission](https://github.com/B1Z0N/homelander/blob/b0e7283b540d853311854d5111bffc0254d5ea85/engine/url-translator.js#L747-L756)).

The `processing` claim prevents two workers from handling one listing concurrently, but a crash after the remote site accepts the form and before `markSent` commits can leave local state inconsistent. Also, because the dedupe hash includes price and not just expose ID, a changed price can create a second sendable listing for the same expose. Individual retry can reset an already-sent row, and `SUBMIT_UNCONFIRMED` can be retried inside `apply()` and later through the generic retry path. No source code can make a non-idempotent website submission exactly-once without a remote idempotency key or independently verifiable post-submit state. Treat uncertain submission as `unknown_outcome`, block automatic retry, and reconcile with the site’s sent-message state or ask the user.

## Proposed minimal architecture (design only)

Reuse the existing Electron daemon, Puppeteer/Chromium profile, SQLite, poller, and site-specific contactor. Preserve one adapter for the chosen site; do not introduce an agent framework or generalized multi-site system for an MVP. Insert a human-review queue between scraping and the existing fill/submit operation:

`poll URL -> normalize listing -> dedupe -> LLM classify -> if match, draft -> persist immutable review -> ping user -> approval -> revalidate binding/session -> fill exact approved draft -> submit once -> verify -> persist outcome`

For each candidate persist the source URL/filter ID, normalized listing ID, listing snapshot and snapshot hash, discovered time, classifier model/prompt version and decision/reason, exact draft text and draft hash, account/profile identity, and review version. Only the `approved` transition can enqueue a send. Approval must bind to a one-time opaque review ID plus the exact listing ID/snapshot version, account/profile ID, message hash, and review version. Any edit, regenerated draft, account switch, materially changed listing snapshot, expiration, or revocation creates a new review/version and invalidates the old approval. The send worker should compare all bound values transactionally, claim once, then submit exactly that text with the authorized user profile.

Recommended states: `discovered -> analyzing -> dismissed` or `draft_ready -> awaiting_approval -> approved -> submitting -> sent`; failures before submission can return to a retryable state. A crash, timeout, navigation loss, or ambiguous confirmation after entering `submitting` becomes `unknown_outcome`, never automatically returns to the send queue. Reconcile via site confirmation/history where reliably available; otherwise surface the ambiguity for user resolution. Record an append-only attempt row with timestamps, idempotency key/review ID, exact message hash, observed confirmation, and error. Reject duplicate approval clicks using a conditional state transition/unique send-attempt constraint.

The notification should show listing facts and source link, why the LLM recommends messaging, the full exact draft, the account identity, and explicit Approve / Dismiss controls. Approval should expire after a short configurable period and require revalidation that listing is still active. The LLM should return a structured decision and draft, but deterministic code should enforce hard constraints (budget, location, must-have requirements, no unsupported persona claims) and reject malformed output. Do not send anything until approval; do not let the LLM choose account or invoke the sender.

## Mapping the five requirements to reuse and changes

1. **Deterministically scrape URL/query filters:** Reuse filter persistence, polling cadence, normalized listing store, and deduplication. Reuse `parseSearchUrl`, `validateSearchUrl`, `buildMobileApiUrl`, and `fetchListings` only for IS24. Before calling it deterministic search coverage, make mobile-rejected/silently ignored criteria explicit failures or visibly accept narrowed semantics, test supported query mapping, and dedupe on stable listing ID independent of price. Page through the fixed newest-first API; define how to detect partial or capped results. It cannot guarantee stable live results or complete all inventory.
2. **LLM decides message or dismiss for new listings:** Add an analysis queue after dedupe. Track an analysis version/result so retries do not silently reinterpret already-reviewed inventory; only analyze newly inserted IDs unless the user explicitly requests reanalysis.
3. **LLM drafts message:** Replace/add to the current fixed template with a structured draft step using listing snapshot plus user-approved persona/preferences. Persist the exact draft and hash; never regenerate after approval.
4. **Ping user with details and exact draft for approval:** Add notification transport and a durable review record. Approval action must reference the immutable review/version. Homelander has local activity UI/history but no verified approval workflow.
5. **Send from user account only after approval:** Reuse the local authenticated browser profile and form-fill contactor for IS24. Gate `apply()` behind the durable approval claim and bind that claim to the exact account/profile and exact message. Its current daemon auto-applies and must be changed; the current generic retry policy must not retry ambiguous submissions.

## MVP scope, tests, and open choices

MVP: one selected listing site and one search URL per user, deterministic parser/normalizer, SQLite queue, structured LLM classifier + draft, a single notification channel, explicit approve/dismiss, local authenticated browser session, one-time send claim, and `unknown_outcome` reconciliation. Defer multiple sites, general agent orchestration, auto-approval, captcha solving, and automatic retries after any possible submission.

Useful tests: stable URL parsing and query preservation; pagination stop/cap behavior; listing identity dedupe across polls and filters; first-run baseline policy; LLM structured-output validation and policy constraints; exact draft hash preserved through notification and send; approval rejected after message/listing/account/version mutation; duplicate click and concurrent worker claim; dismiss never calls sender; send uses only selected profile; failure before submit retries safely; crash/timeout after submit becomes unknown and never retries automatically; positive/negative confirmation transitions; restart recovery for every persisted state.

Unresolved product choices: notification channel/person; which user is the approver and whether approvals are single-use or delegated; target listing site and allowed interaction method; persona facts and prohibited claims; matching preferences (hard filters vs soft ranking); approval expiry and what constitutes a materially changed listing; whether “dismiss” is permanent or may be reconsidered; and the source of truth for reconciling uncertain sends.

## Limits

This is source analysis and design only. No account, browser, or live listing site was accessed. The API request shape and field extraction are verified from source/tests, but their present-day compatibility with IS24 was not live-tested. The adapter is specifically for IS24’s current assumed mobile API and cannot be treated as a generic website scraper. Confirm the chosen site and permitted access method before implementation.
